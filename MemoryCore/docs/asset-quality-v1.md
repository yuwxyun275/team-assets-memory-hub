# 发布前资产内在质量评估（v1）

## 本次实现的边界

本模块回答：**在资产自己声明的适用范围内，正文是否可靠、完整、可使用，结论是否有依据？**

已实现四类资产专项检查、模型内容审阅、原文引用校验、确定性结论、鉴权 API 与本地报告命令。不是用名称/元数据/召回分假装检查正文。

评估单位为一篇 Wiki、一条记忆、一个图切片或一个 SKILL.md 及其配套材料。资产容器包含多篇内容时，一份报告不能代表整个容器。

**当前是显式调用的评估器，不是自动发布闸门。** 不自动改写 approved、confidence、任务状态或推荐权重；不在召回/注入链路调用；不修改 Proxy 缓存。报告通过后仍须人工复核，现有发布接口没有被本模块强制拦截。

## 运行流程

1. 提交正文、内容版本、声明用途、来源材料；API 验证资产身份和权限。
2. 本地规则检查输入大小、明显凭据、Skill 格式/资源、图结构/源码锚点。
3. 未发现基础阻断项时，用已配置模型阅读正文与材料，完成公共和专项评估项。
4. 严格验证返回结构、检查项覆盖、引用位置；不接受不存在的引用或无依据的通过结论。
5. 汇总为通过 / 待补证据 / 发现缺陷，输出逐项依据、修订建议与快照哈希。
6. 负责人核对报告；内容或依据变化后重新提交评估。

这里只提交内容快照，不访问任意 URL、不根据本地路径自动读文件、不执行资产中的指令。内容与来源是否确实出自原生存储，尚未由本模块独立验证。

## 四类资产分别怎么检查

| 类型 | 确定性检查 | 模型必须审阅的内容 |
| --- | --- | --- |
| Wiki | 正文和材料存在性 | 主要事实/规则与来源一致性、适用前提、矛盾与遗漏、可复用性 |
| Chat Memory | 原始对话材料是否提供 | 说话者、否定与条件是否保留；有没有把建议写成事实，把自称成功写成已验证 |
| Code Graph | 节点唯一、边端点存在、路径/版本/仓库/行范围/符号与提交源码相符 | 边的真实含义、切片完整性、静态可能调用与运行时必经路径的区别 |
| Skill | 复用现有 SKILL.md 解析器、正文非空、资源路径安全、声明资源有无提供 | 步骤与依据是否一致、前提和失败边界、能否观察成功/失败、恢复与停止条件 |

四类资产都检查声明范围、内容一致性、安全风险。背景/偏好型 Skill 不强行要求运行测试。操作型 Skill 评估验证设计，但不会把“提供测试输出”当成“本系统执行测试通过”。

### 结论规则

- `pass`：当前所有必需项通过，仅表示声明范围和提交证据下的内容审阅通过。
- `needs_evidence`：没有已识别的缺陷，但至少一项无法确认；需要补材料、重试模型或人工核对。
- `reject`：至少一项发现缺陷；报告区分确定性规则和模型判断，指出对应项，建议修订后重评。

不使用总分抵消严重错误，不用相似度阈值代表内在质量。模型返回格式错误、缺项、伪造引用、服务不可用或超时均不算通过。一个正常引用只能证明引用存在，不能证明事实必然为真；模型仍可能错误理解来源，因此报告固定声明需要人工复核。

## 输入格式

```json
{
  "asset_id": "已登记资产ID",
  "unit_id": "某篇正文或某条记忆的ID",
  "asset_type": "llm_wiki",
  "content_version": "正文版本/提交版本",
  "declared_scope": "业务对象、适用前提及不适用范围",
  "body": "实际待审正文，而不是资产名称或入口链接",
  "sources": [{
    "id": "source-1",
    "kind": "document",
    "locator": "来源标识（不会自动打开）",
    "revision": "来源版本",
    "content": "可以对照核实的原文"
  }]
}
```

`asset_type` 为 `llm_wiki/chat_memory/code_graph/skill`。材料类型为 `document/conversation/code/test_output/resource`。材料 ID 唯一，`asset` 和 `scope` 保留给正文与声明范围。`repository` 是代码材料可选字段，图锚点检查要求与图中仓库一致。

最多 24 份材料、正文/单份材料 60,000 字符、完整快照 240,000 UTF-8 字节。过大时拒绝提交，不悄悄截断后宣称读过全文。请按内容单元拆分并声明切片边界。不得提交未脱敏凭据。有限凭据规则只是防线之一，不是完整 DLP。

图评估快照的 `body` 为 JSON 字符串，其内容结构如下；这是评估接口的规范化格式，不代表任意原生 Code Graph 已自动适配。

```json
{
  "repository": "org/repo", "revision": "commit-or-version",
  "nodes": [{
    "id": "get", "source_id": "code-1", "path": "service.py",
    "symbol": "get_flag", "start_line": 1, "end_line": 4
  }],
  "edges": [{"from": "get", "to": "another-defined-node", "kind": "calls"}]
}
```

行号从 1 开始、包含末行，材料 `content` 从文件第 1 行开始。必须提供被引用的代码材料及匹配的 repository、revision、locator。符号命中仅是锚点检查，不等于证明调用关系。缺少材料是 unknown；已提供但不一致是 fail。未知图格式是 unknown，而不是直接判定资产坏。

## 使用方式

### 本地无网络演示

在 MemoryCore 目录执行（本工作区工具位于 `../node_modules/.bin`）：

```sh
node --import tsx scripts/evaluate-asset-quality.ts \
  --input examples/asset-quality/skill-missing-evidence.json \
  --output /tmp/quality-skill-example

node --import tsx scripts/evaluate-asset-quality.ts \
  --input examples/asset-quality/graph-invalid-edge.json \
  --output /tmp/quality-graph-example
```

输出 `.json` 和可阅读 `.md`，拒绝覆盖已有文件。第一个示例应为待补证据（缺配套测试、未启用内容审阅模型）；第二个为发现缺陷（悬空边）。示例数据是人工构造的测试材料，不是生产资产审核记录。

### 完整模型辅助审阅

在环境中配置 `QUALITY_LLM_BASE_URL`、`QUALITY_LLM_API_KEY`、`QUALITY_LLM_MODEL` 后，在同一命令增加 `--model`。此选项明确启用外部调用，会发送正文、声明范围及提供的材料；请确认数据许可并事先脱敏。默认不发送网络请求。

模型为服务端配置的 OpenAI-compatible 上游，复用项目已有 AI SDK，使用独立的纯文本审阅适配器；不装载文件工具及可选观测后端。超时 60 秒，不自动重试。SDK telemetry 对本次调用关闭。不要把 API Key 写入输入快照、命令参数或报告。

### 受鉴权 API

`POST /v3/meta/asset/quality/evaluate`

沿用现有网关身份头 `x-tdai-service-id`、`x-tdai-user-key` 及部署启用时的 Bearer 认证。请求体为：

```json
{
  "expected_asset_version": 3,
  "snapshot": {"asset_id": "...", "unit_id": "...", "asset_type": "...", "content_version": "...", "declared_scope": "...", "body": "...", "sources": []}
}
```

以上 snapshot 为字段示意，实际值须符合前述格式。仅允许当前团队活跃的资产 owner 或团队 admin。先鉴权后调用模型；资产类型不符返回 400；登记版本变化返回 409；每实例最多两个并发评估，忙时返回 429。元数据登记版本不是正文版本，二者不可互相替代。

API 使用 MemoryCore 网关当前 `llm` 配置，不自动复用或读取 CodeBuddy 私有配置，不允许请求体覆盖模型 URL/API Key。缺配置或上游不可用时，规则检查仍可运行，语义审阅为 unknown。HTTP 日志不输出快照及报告内容。

返回沿用 v3 envelope，data 包含报告、登记团队与登记版本，明确标记 `content_binding=caller_supplied_unverified`。API 当前不持久化报告；调用方应保存 JSON。CLI 可直接保存报告。这防止把用户提交的快照误认为已核验的原生资产内容。

## 什么时候评估

本版本在用户显式提交时触发，适合发布前审阅和内容修订后复评；**尚未自动订阅入库/修订事件**。报告绑定正文、材料、声明范围、内容版本的 SHA-256，并记录 policy/reviewer 版本。任何这些依据变动后，旧报告不能直接沿用。当前没有跨请求评估缓存或报告数据库。

后续可在原生内容读取器、持久化评估任务和发布闸门准备好后接入事件触发。使用后的真实效果反馈应另存，不应直接覆盖这份内在质量结论；这不属于本次实现。

## 验证与已知限制

自动化测试覆盖四类 rubric、缺证据、明显结构错误、凭据阻断、模型伪造引用/缺项/超时、权限、限流、无发布写入、HTTP 日志内容隐藏。

测试中的模型响应是显式测试替身，验证的是工程判定逻辑，**不是模型识别好坏的准确率**。上线前还需要负责人标注的真实正例、反例和证据不足样本，用实际配置上游评估误放行率、误拒率、待确认率，并人工校准 rubric。此阶段没有凭空声明评估准确率或“最佳实践已验证”。

报告是辅助审核证据，不是无误的质量认证；来源真实性、真实运行验证、原生读取、自动发布拦截、异步效果学习均在当前保证范围之外。
