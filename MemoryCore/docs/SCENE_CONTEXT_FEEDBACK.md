# 推荐前场景与使用后效果反馈

实现核对日期：2026-09-11。本文补充 `usage-feedback-v1.md`，不把旧实验改写成新实现的运行记录。

## 数据流

```text
CodeBuddy 当前历史
    ↓ Proxy 在召回前冻结 bounded before 快照
候选召回与排序 ← 查询相同环境、版本和相似问题的历史反馈
    ↓
登记卡片及该会话同版本资产的首次推荐场景
    ↓ 模型按需读取，或短正文直接提供
确认正文进入上游实际输入
    ↓ 创建 exposure，另存正文送达时的事件基线
后台请求一：当前版本正文 + before + 环境
    ↓ 适用 / 需适配 / 不适用 / 未知
后台请求二：当前版本正文 + before + 送达后 events
    ↓ 帮助 / 有害 / 不适用 / 内容错 / 证据不足
引用核验 + 哈希检查 + CAS 提交
    ↓
同一资产、版本、任务、会话的效果回执
    ↓
按新请求的场景重新聚合 U 与限幅适用性修正
```

这不是每次召回都同步调用模型打分。两个审阅在持久化后台观察队列执行，正常对话不等待它们完成。仅发卡片保存目录引用及推荐前快照，未观察到正文送达时不启动本轮使用评价。不实现所有候选资产的事后审阅。

## 1. 推荐前快照

`MemoryProxy/src/injection/injectors/quality-observer.ts` 的 `qualityScene` 收集当前问题、任务描述、活动路径、近期错误和可获取的相关历史事件。它写入后台元数据，不再次注入聊天历史。

- `recommendation-scene/v1` 严格校验字段
- 事件最多 12 条，正文累计最多 16,000 字符，每条最多 4,000 字符
- 任务、当前问题各最多 4,000 字符
- 最多 12 条活动路径和 6 条错误，单值最多 1,000 字符
- 优先近期材料，选中的事件恢复原先相对顺序
- 保留角色、事件 ID、工具调用 ID、逻辑轮次、请求 ID 和截断标记
- 不收录系统消息，过滤明显凭据，不宣称已完成企业 DLP
- `sceneHash` 先经 schema 解析，再固定字段顺序序列化并做 SHA-256

`disclosure-remember` 在团队、用户、Agent、任务、会话作用域保存每个资产版本的首次场景。后续卡片重放、压缩恢复和正文重读不覆盖它。

首次推荐场景和正文送达起点是两个边界。前者解释当时为什么可能适用，后者决定哪些后续事件可以成为效果证据。服务端额外排除 before 事件 ID，客户端漏传 baseline ID 时也不会把这些事件当成新效果。

当前同任务同会话同版本保留第一次推荐场景，不对任务中每一次细分场景切换分别建立独立学习样本。过长历史只保留有界快照，不保证保留全部条件。

## 2. 隔离的适用性审阅

`usage-reviewer.ts` 为 `mode=applicability` 建立独立请求，只发送当前版本资产、before 和环境，不发送未来事件。

输出包括 `verdict`、`reason`、`asset_quote` 和 `citations`。可用结论为 `applicable`、`adapt`、`not_applicable`、`unknown`。

非未知结论必须引用当前资产的连续原文，同时引用 before 中用户条件或非生成文档的真实工具观察。助手自述不能单独证明前提成立。代码校验原文存在、来源、格式及时间边界，不能保证模型语义判断绝对正确。

结论绑定 `scene_hash` 和 `prior-only-applicability/v1`。模型超时、格式及引用错误继续使用已有有限重试、纠错反馈和人工队列。适用性未知是正常结果，不强迫模型补造结论。

## 3. 使用效果审阅与并发安全

第二次请求使用 `mode=effect`。before 作为基线，用来识别推荐前已完成的工作，不能被当成送达后的效果引用。帮助和有害仍要求具体建议与后续可引用行为对应。

- 适用性本身不记 helpful，不直接提高 U
- 未采用或未观察到效果不自动当作负反馈
- 测试已通过但没有新增复用行为，可以返回 unobserved
- 用户明确反馈可以作为观察性证据，但不冒充独立工具验证
- 不把模型 helpful 映射成因果贡献或自动改任务完成状态

有 before 的效果窗口哈希包含场景哈希、环境和后续事件。迟到的效果结果不能覆盖更新后的观察窗口。适用性请求只依赖冻结的 before，提交时可以与并发到达的新后续事件合并。合并读取最新行，通过最多三次 CAS 尝试保持新事件与人工状态。失败留待队列处理。

`effect_receipt` 保存推荐前场景、适用性、使用效果、证据引用、错误、次数与保留期限。`task-receipt` 在鉴权后的当前回执上附加 `scene_feedback` 聚合值，不泄漏其他用户的原始上下文。

## 4. 推荐反馈参数

`utility(..., context, revisionId, before)` 启用新场景查询。必须同团队、资产、版本、repository、task_type 和 environment。缺失可靠环境时保留已有 task-local 隔离，不猜测跨任务可迁移性。

相似性是 `lexical_jaccard/v1`，不是 Embedding：当前问题做 NFKC、小写、技术词提取和中文相邻双字处理。若当前问题为空才回退任务描述。两个问题均至少三项有效词项，交集除并集达到 0.6 才匹配。共享看板描述不会覆盖当前问题差异。旧记录没有 before 时不进入新查询。

同一个 task_id 只取最新观察。不同 task_id 是工程去重单位，不证明统计学独立。没有独立任务样本时不靠多次注入放大票数。

U 保持现有保守收缩计算。正负样本按来源和年龄赋权，模型 0.5，人工 1，再乘 exp(-d/90)。P 为 helpful 权重和，N 为 harmful 权重和。存在正负样本时 U=0.5+(P-N)/(2×(10+P+N))，否则为 null。

适用性另算：A 为 applicable 权重和，B 为 not_applicable 权重和，每份合格模型结论权重 0.5×exp(-d/90)。至少三个不同任务有适用或不适用结论才启用 Δ=0.05×(A-B)/(10+A+B)，否则 Δ=0。adapt 和 unknown 不自动投票。

排序历史特征为 clip((U 或中性 0.5)-旧适用性惩罚+Δ, 0, 1)。已具备新适用性结论的样本不重复进入旧惩罚。`native_assets.py` 继续按现有 0.09 系数使用历史特征。

所有阈值为工程初值，接口返回 `calibrated=false`。不自动调整 Q 四维权重、全局排序系数、旧版正文或发布状态。内容错误提交单独复评请求。

## 5. 验证与部署

- Core 相关套件 149 项通过，包括新增前后文隔离、CAS 合并、快照保留、三任务门槛与旧记录兼容测试
- Proxy 全套 110 项通过，覆盖两类模型协议的首次快照传递、历史重放与实际正文送达
- Python 排序适配与渐进披露 14 项通过
- Panel 类型检查及构建通过
- Core 针对新增模块的 TypeScript 检查通过
- 三组开发者构造回归通过真实部署 API 和配置中的 DeepSeek 异步审阅，分别得到 applicable/helpful、not_applicable/not_applicable、applicable/unobserved
- 这三组不是新一轮桌面 CodeBuddy 编码实验，不能用于报告任务完成率、推荐准确率或缓存提升

运行三组场景的脚本：`evaluation/asset_recommendation_bench/verify-scene-feedback.mjs`。它会创建演示任务并触发真实模型，保留结果，不把期望标签发送给模型。

部署后只读检查：`evaluation/asset_recommendation_bench/verify-scene-feedback-state.mjs`。它读取回执、Q、版本和服务健康，零模型调用。

部署脚本：`deploy/quality-v2/deploy-scene-feedback.mjs`。`--apply` 执行，`--component core|hub|proxy` 可分组件。保留旧容器与数据备份，健康失败恢复原容器。排序服务使用既有只读源码挂载，代码更改后需重启加载。配置和备份可能含凭据，不对外分享。

证据目录：`output/scene-feedback-20260911/`。最初三组模型记录的 reviewer 标签仍为旧 gateway 包装的 usage-review/5，但运行的是前后文新版请求。新 gateway 已从 factory 读取 usage-review/6 标签。保留原审计记录，不回写修改标签。

## 6. 企业应用边界

本实现提供可审计的观察性反馈闭环，不是完整因果归因系统。仍需专家黄金集校准、同义场景匹配改进、多实例并发压测、长期样本与隐私保留治理。当前不会自动生成资产适用标签或重写资产正文。
