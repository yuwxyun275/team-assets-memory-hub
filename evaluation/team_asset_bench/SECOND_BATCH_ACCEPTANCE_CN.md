# 第二批（第二版）实现与验收说明

## 这次真正补了什么

第一批证明了 `CodeBuddy → MemoryProxy → 团队资产编排器 → Memory Hub` 可以跑通。第二批把“演示能跑”进一步收紧为“证据不会轻易丢、任务不会被轻易误判完成、贡献不能由 Agent 自报”。

### 1. Trace 与证据可恢复

- 运行态改为 SQLite WAL 持久化，保存 Context Package、任务画像、验收契约、工具观测、候选资产和反事实结果。
- 六阶段事件也进入事务型 SQLite Ledger。
- 同一 `trace + task + asset + state` 具有唯一约束，因此 MemoryProxy 重试不会生成重复证据。
- 服务重启后可以继续读取同一 Trace；回执显示“本 Trace 已通过重启恢复”。

适用边界：当前是单机持久化方案，适合本地部署、比赛验收和单节点服务；若做多副本生产集群，应替换为 PostgreSQL/分布式事件存储和共享幂等键。

### 2. 任务是否完成由任务看板验收契约决定

Memory Hub Task 元数据现在包含 `team_asset_acceptance`：

- 必须通过的 9 个具名测试；
- 必须观察到目标代码修改；
- 允许修改的目标路径；
- 契约版本和来源。

因此，“4 项资产都通过各自代表性测试”只说明资产已验证，不等于任务完成。只有同时满足以下条件才会把 Task 更新为完成：

1. 选中的资产确实影响了工具调用；
2. 每项已采用资产都有测试证据；
3. 9/9 项任务验收测试均具名通过；
4. `feature_flags/service.py` 的修改被真实工具调用观测到。

Memory Hub Task 抽屉直接展示 `测试 9/9、资产采用 4/4、资产验证 4/4`，未完成时列出缺失或失败的测试。

### 3. contributed 改为服务器自动、失败闭锁

`contributed` 不再接受 Agent 或演示脚本提交的文件路径与“我认为有效”声明。服务器仅在：

1. Task 验收契约已经完成；
2. 找到与当前仓库、版本、任务类型匹配的可信反事实评测；
3. 当前每项资产在单资产消融中确有正向差异；

三个条件都成立时，自动追加贡献事件。回执保存评测文件内容的 SHA-256 引用，而不是相信调用方传来的路径。没有匹配评测时状态为 `unverified`，不会夸大为“产生贡献”。

### 4. MemoryProxy 可靠重试

- 编排器请求遇到网络异常、429 或 5xx 时最多重试 3 次。
- 每次重试携带稳定的 SHA-256 幂等键。
- 鉴权/契约类 4xx 不重试，避免放大错误请求。
- 三次均失败仍然 fail-open：不阻断 CodeBuddy 调用上游模型，但不会伪造资产注入确认。

### 5. 候选资产仍需团队审核

只有 Task 完整验收后才生成候选资产。候选内容进入 Memory Hub 的 `candidate` 状态，默认不会被后续 Coding Agent 注入；必须由团队成员选择“发布”或“拒绝/归档”。

## 自动测试覆盖

- Python：14 项通过，新增覆盖：
  - 4/9 测试时禁止完成、禁止贡献、禁止生成候选；
  - 9/9 测试时自动完成并自动贡献；
  - 编排器重启后 Trace、完成判定和贡献证据完整恢复；
  - 重复注入回调不产生重复事件。
- MemoryProxy：6 项通过，新增覆盖 503 后使用同一幂等键重试成功。
- Memory Hub：生产镜像构建用于校验 TypeScript 与前端资源。

## 一句话理解第二版

第一版回答“团队资产有没有进入 CodeBuddy、有没有影响操作”；第二版继续回答“服务重启后证据还在不在、任务凭什么算完成、贡献是谁证明的、网络抖动会不会把证据链弄断”。
