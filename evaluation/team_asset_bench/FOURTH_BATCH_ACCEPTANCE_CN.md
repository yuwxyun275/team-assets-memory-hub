# 第四批：自动验证发现、保守可信归因与生产化加固

## 1. 这一批解决什么问题

前三批已经能够在 CodeBuddy 会话中逐轮推荐团队资产，并把任务结果回传到 Memory Hub。
第四批针对真实落地中最容易被夸大的三件事做加固：

1. 不再把演示项目预先写死的“9 项测试”当作通用方案；验证要求应优先来自目标仓库和 CI。
2. 不再因为资产被注入、任务测试通过，就推断该资产影响了代码；必须建立可核验的因果关联。
3. 不把单次确定性参考 Agent 的结果包装成真实模型收益；提供真正的多轮模型评测器，并明确标注是否实际运行。

这意味着系统同时维护三类互不替代的结论：

- **推荐结论**：当前轮应该给 CodeBuddy 哪些最小团队上下文。
- **归因结论**：哪些资产确实影响了决策、代码或验证动作。
- **结果结论**：目标代码是否通过仓库测试或企业 CI。

## 2. 仓库自带验证的自动发现

`verification_discovery.py` 对 Python 精品项目进行只读静态分析：

- 解析 pytest 测试函数与类方法，不导入、不执行被测代码；
- 读取 `pyproject.toml`、`pytest.ini`、`setup.cfg`、`tox.ini` 中的 pytest 配置；
- 发现 GitHub Actions、GitLab CI 和 Jenkinsfile；
- 根据目标变更路径筛选相关测试；
- 输出安全的 `argv` 数组清单、具名测试和仓库指纹，拒绝拼接任意 shell 字符串。

本地体验仓库实际自动发现到 3 项 pytest 测试，并由本地 CI 适配器执行，结果为 3/3
通过。演示中的 9/9 是该任务包原有 3 项公开测试与 6 项隐藏测试的具体结果，不是所有
新任务都必须固定为 9 项。

复现命令：

```bash
cd evaluation/team_asset_bench
PYTHONPATH=. python3 -m team_asset_bench discover-verification \
  --workspace projects/feature_flag_service/base \
  --changed-path feature_flags/service.py
```

## 3. 从“模型说用了”升级为可核验归因

`attribution.py` 将 `used` 和 `validated` 分成两道门槛。

### 3.1 采用证据

资产进入 `used` 至少需要组合证据，而不是单一自述：

- CodeBuddy 输出资产 ID、作用目标和原因的结构化声明；
- 工具轨迹中存在真实编辑或测试动作；
- Git Diff 的变更路径与资产声明的作用范围匹配；
- 变更内容生成稳定哈希，用于审计而不保存整段敏感代码。

系统据此给出归因置信度和强/中/弱等级。没有足够证据时，资产最多停留在 `injected`，
不能宣称“已使用”。

### 3.2 验证证据

资产从 `used` 进入 `validated` 还需要：

- 资产自己的验证提示与实际通过的**具名测试**相匹配；
- CI 或本地验证结果带有独立证据摘要；
- 变更路径、Commit/工作区指纹与本次运行一致。

因此，“任务整体测试通过”和“某项资产被验证有效”可以得出不同结论。推荐 5 项、采用并
验证 3 项是完全正常的；另外 2 项不会搭便车获得贡献状态。

## 4. CI 信任边界

CI 适配器遵循以下边界：

- 本地执行只接收经过审核的参数数组，并限制工作目录与超时；
- GitHub Actions、GitLab CI、Jenkins 等远程结果必须绑定 Commit SHA；
- 只有通过受信 Webhook 校验的远程回执才可作为强验证证据；
- 手工复制的日志和未经校验的重放只能作为弱参考，不能自动把资产提升为贡献状态。

系统不要求开发者为每次对话手写测试。最佳顺序是：复用仓库测试与 CI → 根据验收标准
匹配已有测试 → 对真正缺失的业务契约补测试。验收标准用于说明“什么算完成”，不等于
让模型无条件临时生成一套自证正确的测试。

## 5. 更稳健的反馈学习

每轮推荐后的反馈分为：

- `useful`：存在采用或验证证据，进入正向学习；
- `not_applicable`：当前场景明确不适用，轻度降权；
- `duplicate`：与其他资产重复，降权并便于后续合并；
- `stale`：版本或时效过期，必须附可核验原因；
- `incorrect`：内容错误，必须附可核验原因并显著降权；
- `unobserved`：没有观察到采用证据，保持中性。

这一设计避免把“模型没用到”粗暴等同于“资产没价值”，同时又能让明确无用的推荐在相似
任务中逐渐减少。排序还考虑来源可靠性、仓库与版本兼容、相关性、新鲜度和 Token 成本。

## 6. 已完成回执不会被不完整重试覆盖

真实使用中，同一个 Task 可能被重复打开、重试或产生残缺 Trace。V4 增加权威回执合并
策略：

- 已完成且证据更强的回执继续作为任务看板主回执；
- 后续部分尝试保存为 `asset_evidence_latest_attempt`；
- 最近 20 次尝试进入 `asset_evidence_history`，便于审计；
- 低质量重试不能把 9/9 和完整六阶段链路覆盖为 0/9。

## 7. 真实模型多轮评测器

`multi_turn_eval.py` 提供 6 轮中文场景、4 个对照组和默认 3 次重复：

- 动态最小上下文；
- 静态最小上下文；
- 全量上下文；
- 无团队资产。

评测记录每轮推荐、模型判定的有用资产、精确率、Token 和响应哈希，不保存模型完整回复。
模型层使用 OpenAI Chat Completions 兼容接口，不绑定具体厂商。

```bash
cd evaluation/team_asset_bench
export TEAM_ASSET_ALLOW_EXTERNAL_MODEL=true
export TEAM_ASSET_EVAL_REPETITIONS=3
PYTHONPATH=. python3 -m team_asset_bench evaluate-multi-turn-live
```

运行外部模型前必须明确确认目标端点获准接收构造的团队资产。目前评测器已经实现并完成
本地单元测试，但本次没有把资产发送到外部 DeepSeek 端点，因此不报告真实模型效果增益。

## 9. 当前边界与下一步

- 自动验证发现当前以 Python/pytest 精品项目为主；后续可增加 Jest、Maven、Go test 等适配器。
- 企业环境中的本地执行器应进一步放入无网络、只读挂载、限 CPU/内存的短生命周期容器。
- 外部真实模型的多次运行尚待对目标上游的明确数据授权；在此之前不把参考策略结果冒充模型收益。
- 任意原始 Session、Wiki、Skill、Code Graph 的自动抽取仍是后续阶段；当前中文资产由团队构造并保留来源锚点。

这套 V4 的核心价值不是“多召回几个文档”，而是让团队经验在正确的会话轮次被最小化推荐，
并用代码变更、具名测试和可信 CI 回执证明它是否真的产生了价值。
